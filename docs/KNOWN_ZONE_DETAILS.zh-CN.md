# 已探索地块的资源、矿藏余量与野兽

`known_zone_details`是一个独立的可选组件，记录本局本人已经探索的地块。它在玩家正常开图后后台采样，不要求截图或逐块点选。没有探索的地块不会补出资源和野兽；采集期间读取失败也不会用过去的地图冒充当前状态。

当前实现先限定**Standard类型的普通单人FreeForAll**已审查分支，按已核游戏双指纹读取。氏族会改变实际生产和人与野兽的关系，因此默认资源属性与最终产能、是否敌对分别保存。真实短段验证尚未运行；不能把离线测试、成功安装或旧局本方矿数据当成这个新组件已经完成实局验收。多人和不支持的模式返回`unsupported_context`，本人库存、职业、劳动、增长等既有组件继续记录。

## 一块地包含哪些数据

组件位于`player-observations.ndjson`的每个有效本人观察以及`latest.json`中，通过当前session下的`zone_id`连接`map_observation`和`base_neighborhood`。只接受本局、本人已知集合中精确的地块对象；同一个数字ID在另一局重用，不会继承旧资源。

| 内容 | 表达方式 | 不能据此推断 |
|---|---|---|
| 自然资源 | 农田、鹿源、鱼源、森林、符文石、石圈、石矿和铁矿，按kind区分 | 缺少图标、缺字段或读取失败不表示没有该资源 |
| 默认属性 | 每资源行的`reference_properties`记录候选生产渠道、自然对象的直接指派槽和配置加成 | 自然对象的指派槽不是建好农田/矿场后的最终岗位容量，默认属性也不是当前最终产率 |
| 矿点 | `natural_object_uid`关联同局矿点，保存`remaining_contains_raw`、`next_extraction_progress_raw`及同资源聚合量 | 进度不是剩余矿量百分比，也不是某个矿工的个人到账；UID不能跨电脑或跨局合并 |
| 普通野兽 | 首版限定无玩家归属的`Wolf`、`Bear`及支持范围内的计数 | 无玩家归属不自动等于敌对；不等于完整中立驻军或可直接殖民 |
| 隐藏属性 | `TallGrass`、`HidingGrass`是否被完整分类，以及相关覆盖状态 | 缺资源图标不证明没有草；未知不能填false |
| 数据质量 | 每地资源与野兽分别有状态和原因；组件保留采样时间跨度及非原子标记 | 一项失败不使另一项变成零，也不证明整张地图已完整采齐 |

顶层`status=partial`表示只支持受限定的自然资源与野兽范围，不代表覆盖所有地块内容。每地`resources_status`、`wildlife_status`和相应原因需要一起使用。只有明确支持且完整读取的种类范围才能解释零计数；特殊隐藏对象、未知字段和失败集合不能补零。

## 资源不是同一种库存

石矿和铁矿的原生`Building.state.contains`保存剩余量；同一个state中的`progress`是下一次开采完成的共享进度。两个矿工共同推进同一矿点，不能把进度给两个人各算一份产出。原生nullable字段没有读到时保持null；只有明确读到0才有零余量证据。

游戏的矿量界面通常显示**整块地同资源矿点的contains之和向上取整**。单矿原始小数、全地总量和显示整数是不同字段。集合或可见条件不完整时，聚合结果保持未知。自然矿对象消失也不能直接补0：需要区分耗尽、移除、换局和读取竞争。

每矿的`natural_object_uid`只在同一采集session中用于连接前后观察；与已殖民后的`labor.buildings.uid`相同且类型/地块匹配时，可以建立同矿关联。不要用列表顺序代替身份，也不要假定跨局、转换或对象移除后仍是同一矿。

其他资源按其游戏机制解释：

- 农田提供特定生产机会，不是一个不断扣减的食物矿藏。
- 鱼源、森林和知识地也不能统一填写“还剩多少食物、木材或知识”。不适用与读取失败分别表示。
- 鹿源的生成上限和生成参数不是固定食物库存，更不等于每次采样都有相同数量的鹿。
- 符文石与石圈分开。普通配置中的岗位容量不同；石圈的局部知识加成也不能当作符文石的同一属性。

`reference_properties.semantics=verified_default_configuration_not_effective_yield`明确标记默认配置；`depletion_model`区分`finite_mineral`、`renewing_deer_source`和`production_opportunity`。`fixed_assignment_slots`只表达自然对象直接指派的配置，未配置的矿点保留null；不能解释为矿场可用工位为0。配置候选渠道也不表示同时产出多种资源，例如Lore/Faith仍取决于氏族与规则。局部倍率带适用范围，不能直接覆盖氏族的实际收益。因此运营分析应先看资源机会、岗位与默认加成，再结合本方氏族、科技、劳动输入和实际全局产消判断收益。

## 野兽与视野

当前游戏普通实体的可见分支中，本人地块已探索可以满足基础发现条件，不普遍要求侦察兵一直站在该地。采集器依据当前版本的字段与规则重建受支持分支，不执行游戏getter。

仍需检查禁用、`scriptVisible`覆盖、草丛隐蔽和单位特殊状态。首版对不能确定的草丛/特殊条件保留未覆盖原因，不依靠“这里应该看得见”放行。普通狼熊运行时可能是`ent.Foe`；Kaija的`BearMaiden`与普通`Bear`分开，己方熊不会作为野熊计数。当前狼数量为0也不能证明没有巢穴或以后不会生成、迁入。

后台读取只增加本局已探索自然对象和限定无玩家归属的狼熊数据；不读取玩家姓名、账号、对手经济或完整敌军清单。当前组件没有把普通单人的规则认证为3v3可用。

当前鱼源分支只支持已物化`seaShoal=false`的普通鱼点；海鱼或尚未物化的判定保持partial，不解释成没有鱼。草丛分支目前也采取保守覆盖，不承诺所有特殊隐藏规则已重建。

## 查看与诊断

在仓库根目录读取本地捕获的最后一帧：

```powershell
python scripts/show_known_zones.py --capture captures/你的采集目录
```

命令按游戏年月展示地块资源、矿量、狼熊和未知原因，不会启动游戏或上传数据。旧版捕获没有这个组件时明确报告未采集；不会拿当前规则或历史默认量补出旧局未探索的信息。

记录时同时看：

- `health.ndjson`中的`known_zone_details_status`、`known_zone_details_unknown_fields`。
- `component_diagnostics.known_zone_details`中的来源状态、投影状态和原因代码。原始异常文字、内存地址和安装路径不进入这个诊断树。
- 本地`manifest.json`中的`last_known_zone_details`。它只摘要最后一帧状态、已观察地块数和游戏秒；未知/不支持时数量为null，不是0，也不是全局覆盖率。

缺失、`unavailable`、`unsupported_context`或`rejected`都不应阻止核心本人观察追加。默认记录只留本机。公开贡献仍需本人的该局分享授权，经过固定字段投影和独立验证，不上传原始研究流。

## 最小真人验收

用户正常操作普通熊族单人短段即可，不需要AI操作游戏：

1. 未探索时没有隐藏资源输出；发现一块未殖民资源地后，资源种类、矿量和狼熊与游戏显示相容。
2. 殖民前后是本局同一个自然对象，矿量不会因殖民重置成默认值。
3. 采矿时分别检查contains减少和下一单位progress推进；暂停不增加游戏时间或开采工作。
4. 清野前后检查支持范围内的计数；Kaija经过时不变成普通野熊。
5. 草丛和其他未覆盖分支保留未知；面板关闭、切换不使后台数据归零。
6. 返回菜单、换局复用地块ID或读取失败不继承旧对象；该组件失败时经济和人口记录继续。

完成这些检查后才能更新实局验证记录。源码安装、合成内存测试及贡献包内部一致性校验均不能代替真人短段验收。
