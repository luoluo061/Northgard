# 按北境之地的机制理解采集数据

这份文档面向玩家和分析者。我们要回答的不是“这局最终攒了多少粮”，而是：**在指定年月、氏族、科技与目标下，人口怎样把时间转成资源和胜利条件。**

采样是非原子的状态观察，并非游戏内完整账本。所有结论都应带采集版本、游戏双指纹、session/run/segment、游戏时间与证据层级。

## 1. 时间是共同坐标

`game_time_seconds`来自游戏模拟时钟。0=A800年3月，60游戏秒=一个月，720=一年。暂停不推进时钟。`captured_at`是墙钟，只用于排查采集延迟，不乘产量。

月初[0,20)、月中[20,40)、月末[40,60)只是复盘展示的分桶；游戏不在三个分界点统一发工资。一次调岗可能月初指派、月中转职、月末才成为生产候选，必须保留跨段链条。

读档、重开、重新连接、原生日志分支变化会改变身份或分段。看起来同为A800年5月的两个记录可能来自不同局，不能仅凭年月连接。读取失败也不能用上一帧填满。

## 2. 人口不等于单位对象数

`population`是当前已核规则下的普通人口口径，普通军人也占人口；装甲熊、英雄、护卫等单位另有规则。`units.length`只能叫单位实体数。其他氏族、特殊单位和模式未验证时，人口可能未知，不能回退成单位总数。

人数、职业和部队类型已经可以采到：`units[].uid`是同局单位身份，`units[].kind`是当前职业/类型。例如`Farmer→Sailor`表示同一个人从农民转水手，`Woodcutter→AxeWielder`表示木工转掷斧兵。按kind计数即可得到当帧职业和兵种构成；采集最终manifest也会保存`last_own_unit_kind_counts`摘要。部队种类并不缺失，尚缺的是把每名单位的最终经济贡献完整分解。

常见字段对应：`Villager`村民、`Farmer`农民、`Woodcutter`伐木工、`Miner`矿工、`Sailor`水手、`RuneMaster`符文师、`InnKeeper`酿酒师、`Scout`侦察、`Healer`治疗者、`Smith`铁匠、`Warrior`战士、`AxeWielder`掷斧兵、`ShieldBearer`盾兵、`Maiden`英雄、`BearMaiden`装甲熊。可见的职业变化不自动证明是玩家主动点击，复盘同时保留指派和状态变化证据。

分析时要分开四层：

| 层次 | 回答什么 | 不能替代什么 |
|---|---|---|
| 职业kind | 这个人现在叫什么职业 | 不保证在岗或生产 |
| assign_to / assigned名单 | 想去哪里、建筑记录分配了谁 | 不保证已经到位 |
| cur_job / produce / has_no_work / enabled | 当前任务与生产门控输入 | 不保证已经结算该资源 |
| 实际原生产消缓存 | 整个经济系统当期产消率 | 无法直接分摊成每人实际贡献 |

画面上搬运也不一定停产；游戏部分运输路径仍保持working。不能按单位移动距离或动画次数机械扣粮木收益。

## 3. 粮食从哪里来，库存为什么变

经济组件`economy.resources.Food/Wood/Money`保留库存、原生缓存时钟、毛产、消费、净流与累计正产计数。率的单位是**资源/游戏秒**。普通界面常有倍率格式化，分析以原始单位为准。

基本关系是：

```text
库存变化 = 连续实际入库 − 连续消费 − 一次性支付 + 一次性收入
净流速 = 毛产速率 − 消费速率
```

Wheat、Meat、Fish等生产分支最终归并为Food；Food单个生产槽不是总粮。`gross_aggregate_per_game_second`有其明确的缓存复算来源，不能再把自然食物分支重复加一遍。累计`total_produced_counter`是总经济计数，不是某个工人的贡献。

殖民、盛宴、建造、升级、招兵、贸易、奖励等都会造成库存跳变。看到100粮突然少了80，不代表工人少产80；必须连事件、付款状态和连续产消一起检查。外层库存和经济子组件可能在不同读取时刻，不能拼成原子前后对照。

## 4. 容量会改变劳动的实际入库价值

粮仓或其他上限使潜在产出和实际入库不同。正净流并不保证全部进入库存；封顶期间可出现生产计数/库存不按简单净值增长。

额外一名农民的价值取决于是否能入库，以及即将是否要支付盛宴或殖民。暂时封顶也可能是有意备粮。容量来源有`verified`/规则推导等口径，不能把后验模型当作直接读到的运行值。

## 5. 逐人产出：目前读到的是输入，不是完整工资条

当前版本的`Unit.getProduction`、`getProductionBonus`和`canProduce`是动态计算函数。它们的结果没有完整保留为外部可读的逐人持久结算表。本项目不执行这些游戏函数。

因此`labor.units[].native_actual_rate`、`native_settled_amount`、`model_effective_rate`目前明确为null；`native_individual_rates_available=false`。这不是此人零产出。

新增可采输入包括：本人科技与工具升级记录、人口/幸福缓存、冬季状态、盛宴/过劳时点、单位任务与门控、伤病/状态、本人和自有地块/建筑的affect时点与flags、港口选择、矿藏/建筑状态进度。每项都可能独立缺失，查看`status`、`reason_codes`、`unknown_fields`。

`configuration_candidates`中的`configured_base_q`来自玩家本机已核对的规则定义。它表示配置候选，不表示这个资源分支实际满足条件，更不能把所有候选q相加。完整限制见[逐人实产边界](UNIT_PRODUCTION_LIMITS.md)。

## 6. 各种加成不是把百分比全乘起来

生产链通常是基础岗位/建筑条件→氏族/科技/工具/区域/临时状态→惩罚→汇总。很多修正在同一个modifier里相加，部分冬罚又有独立scale或基础值替换。

以已核熊族机制为例：冬季天赋减少冬罚幅度，不是给所有产出直接乘0.7；冬节还会影响冬季食耗和非粮生产。利斧与造船针对的岗位不同，局部英雄/熊加成需要满足地块条件。能学鱼叉不等于这一局已经学了鱼叉。

`researched_tech_entries`和`upgraded_unit_entries`是原生存储记录。附加科技来源、借用科技、特殊模式等可能走其他路径，所以“普通map没这个键”不一定等于游戏hasTech=false。affect结束时间也可能是哨兵值，不能只因记录里有一个名字就声称当前buff生效。

研究者应保存：规则ID、观察值、何时获得、作用对象、空间条件、叠加位置和证据来源。暂未解码的修正保留未知，不用凑总倍率。

## 7. 现有人调岗与新增人口是两笔账

同一个普通人从粮转木仍需吃饭。比较两方案时，共同且不变的食耗抵消；只计改变了的产出、维持费、一次性转职/建筑费用和过渡损失，不能重复扣本人食耗。

新增人口则应比较全体消费的`C(P+1)-C(P)`。人口规模可能同时提高原有成员的食耗，不是只多一张嘴。再加出生等待、住房、幸福度和未来可用劳力时间。因而没有脱离人口规模、季节和氏族的永久“一人养几人”。

粮、木、金、矿物、知识、声望和军事不是同一单位。先检查下一项计划的资源储备与期限，再比较候选用途。缺50木才能及时补房时，木的边际价值来自解除出生瓶颈；临战缺招兵钱时，水手可能比增加库存粮更迫切。

## 8. 转岗延迟按阶段和区间记录

`actions.labor_transitions`将同uid连接到：指派目标变化、任务/地块变化、职业变化、生产候选恢复。每个阶段都有前一有效样本和首次观察样本的时间区间，延迟给上下界。

这不是点击时刻；`assignment→candidate`也不是纯走路时间，其中可能含转职、任务等待与采样误差。`actual_resource_production_confirmed=false`必须保留。记录断裂、读档、长缺口或单位消失时，链条标中断/未完成；不能把消失直接叫死亡，也不能跨局拼接。

已知旧局短窗曾观察到农民转水手先减少粮毛产、约7.53游戏秒后才增加金毛产。这只能说明该次交换的局部变化，不能当本版本所有水手的固定系数。新数据要保存前后所有相关状态，供后续隔离归因。

## 9. 增长进度解释住房与幸福度的价值

`population_growth.town_halls[].growth_progress`是市政厅直接存储的进度。`native_inputs.current_happiness`等为缓存输入；`growth_bonus`是动态函数结果，当前不完整求值，保持null。

普通已核熊/乌鸦路径下，下一招募阈值可按`55+5P`建模；它明确写在`model`里，不能说是直接读取的getter结果。住房上限、幸福非正、增长禁用等可观察阻塞输入会单列，但城镇战斗/出生位置与特殊规则可能仍不完整。

`observed_progress_intervals`在同身份、短间隔、端点人口/幸福/修正一致、没有进度回落时计算观察斜率。条件ETA只表示“如果这段斜率继续，多久达到阈值”，不是保证多久出生。暂停、出生重置、读错误和状态变化会断开计算。详见[GROWTH_AND_TRANSITIONS.md](GROWTH_AND_TRANSITIONS.md)。

## 10. 殖民与建造必须连到上岗

新地不是付款后立刻产粮木。应连接：发现→清地/通路（若有证据）→支付殖民费→归属改变→施工支付→施工占人→建筑完成→派工→生产候选→全局产消变化。

每一段都有材料成本、原岗机会成本与等待时间。矿物是共享矿藏进度达到阈值后的离散到账，不按每名矿工连续小数直接进入库存。建筑状态progress/contains要结合对象类型理解，不能把任意progress都叫施工或挖矿进度。

旧局没有记录的付款/地图字段不会因新采集器出现而自动恢复。新局也没有每次点击或失败命令的完整记录；建筑消失可能由取消、摧毁或读取切换造成。

## 11. 怎样贡献能检验的玩家经验

在同一条游戏时间轴标明“我观察到什么”“我当时为什么这么选”“我怀疑什么机制”“什么条件下不适用”。例子：

> A801年9月月中，住房接近上限且升级后木材不足。我倾向先预留房屋材料。但如果首冬粮食会先耗尽，应比较补农和补房各自阻断的时间。想验证：幸福进度是否真的因住房停止、提前补房能多获得多少可用劳力时间。

这是一条带条件的经验，不是已经证明的最优顺序。请同时提供反例、地图条件、目标、难度、氏族和已学知识。填写方法见[玩家反馈](PLAYER_FEEDBACK.md)，数据包标签见[贡献协议](DATA_CONTRIBUTION.md)。

## 12. 后续统一分析的验收顺序

1. 先验版本、本人身份、时钟、来源、缺口与分段。
2. 检查各组件成功/partial/rejected比例，缺失值不能补零。
3. 将劳动阶段、增长、知识、地块、建筑和支付放回同一时间轴。
4. 先核连续库存闭合，再做单次劳动变化的受控前后对照。
5. 按氏族/科技/季节/建筑/地块/健康分层校准，保留不适用条件。
6. 以资源储备、目标期限和反事实为依据比较劳动用途；不由一次胜利倒推全部操作正确。

数据和解释永远分层：直接存储读数、按已核公式计算、采样区间估计、高置信归因、玩家经验、未知。当前开发版的实局验收范围见[VALIDATION_STATUS.md](VALIDATION_STATUS.md)。
