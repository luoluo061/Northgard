# 逐人产出：当前能读取什么，什么仍然缺失

本页说明 `labor` 组件的口径，供安装采集器的 Codex、参与采样的玩家和后续分析者共同使用。版本绑定 Northgard `v4.3.29.43387` / Steam Build `25096976`。游戏更新后必须重新验证，不能沿用旧偏移和旧机制结论。

逐人输入已有本人单人短段观测；完整机制模型、控制实验和真实3v3仍未验收。历史没有记录的字段不会补回。代码测试与局内观察都不等于完整逐人实产已经闭合。

## 1. 为什么还不能直接报告“这个农民刚刚产了多少粮”

当前已核对的运行链路是：

```text
单位任务与工作状态、所在区块、指派建筑
  → Unit.canProduce
  → Unit.getProduceData / getProduceValue
  → Unit.getProduction
      → getProductionBonus
      → applyProductionMalus / getStatusProductionMalus
  → 玩家 Production 汇总器
  → ResourcesComponent 常规结算
  → 粮、木、金币库存
```

已核对的 `ent.Unit`、`UnitVariables` 和 `cachePhase` 字段没有可持续读取的“该单位最终每秒产量”或“该单位累计到账量”缓存。`cachePhase` 保存战斗、移动、生命等阶段数据，不能把名称中的 cache 当作生产缓存。

`ResourcesComponent.detailedProduction` 也不是逐人明细表。它是一个计算器对象；`getDetailedProduction` 每次创建临时 `DetailedAccumulator`、重新计算，然后返回细分结果。普通 `production` 对象同样用于计算。已经读到的 `lastResProd`、`lastResCons`、`currentFood/currentWood/currentMoney` 是玩家汇总率缓存，不能除以岗位人数就宣称读到了每个人的真实率。

本采集器仅调用操作系统的只读进程接口和本地解析代码。它不远程执行游戏函数、不注入、不写内存。特别是不能为了取得“最终率”而调用游戏 getter：已核字节码中 `canProduce` 的部分分支甚至会调用 `setWorking`，因此 getter 名称并不保证没有副作用。

所以当前字段明确写成：

| 字段 | 当前值 | 正确解释 |
|---|---|---|
| `native_actual_rate` | `null` | 没有取得该单位最终原生结算率 |
| `native_settled_amount` | `null` | 没有逐人已到账量缓存可读 |
| `model_effective_rate` | `null` | 尚未完成覆盖全部适用条件的公式重建 |
| `can_produce` | `null` | 没有执行游戏中的生产资格判断 |
| `inputs.produce` | 如 `Wheat`、`Wood`、`Sailors` 或 `null` | 当前生产标签；不是已到账量，也不等于一定正在有效生产 |
| `configuration_candidates[].configured_base_q` | 配置中的数值或 `null` | 本机游戏配置的候选基础参数；不是当前实际率 |

“未取得”必须保留 `null`，不能补零。零意味着已知没有产出，含义不同。本页也不排除未来在其他 UI 临时对象中找到短暂明细；但临时 UI 明细不等于覆盖所有工人的稳定结算记录，不能据此承诺完整逐人实产。

## 2. 新增劳动输入，怎样联系到游戏理解

### 自己每名单位

使用本局单位 UID 连接前后快照，采集以下字段。UID 是局内实体编号，不是 Steam 账号。

| 字段组 | 游戏里对应的含义 | 分析时必须保留的限制 |
|---|---|---|
| `kind`、`assigned_job`、`cur_job_kind` | 当前职业、已指派岗位、当前任务类型 | 三者改变不一定同时发生；任务枚举的对象参数不导出 |
| `produce`、`has_no_work`、`just_assigned` | 当前生产标签、无工作标记、刚指派标记 | 是生产判断输入，不能单凭其中一个重建全部生产资格 |
| `assignment` | 已验证为自己建筑的指派目标，以及是否在同一块地 | 未验证的目标只标未知，不导出敌人对象或任意引用 |
| `enabled`、`hit_life`、`sick_counter`、`sick_reason` | 原生启用、伤病相关读数 | `hitLife` 不是“剩余生命”的通用同义词；不凭这个字段猜死亡原因 |
| `status`、`status_timer`、`flags` | 原生状态和位标记 | 未解码的 flags 保留原整数，不擅自命名百分比加成 |
| `effects` | 本人实体已保存的效果名与 `raw_end_time` | 时间可能有哨兵值，也可能已过期；这不是已验证的“当前生效倍率表” |

所有单位都再次验证 `owner == 本机人类玩家`。关键身份、职业、所在区块、指派和生产字段在读取前后比较；观测到变化会丢弃该单位本次新组件数据，避免把半次调岗拼成一个稳定状态。不同读取之间仍不是原子快照，必须保留采样时间范围。

### 自己的科技与工具

`player_context.researched_tech_entries` 保存自己 `TechComponent.researchedTechs` 的标量条目，`upgraded_unit_entries` 保存自己 `UpgradesComponent.upgradedUnits` 的标量条目。它们可以用于连接“刚学了哪项知识”“哪类工具刚完成升级”和随后变化的玩家资源率。

这里没有把条目值强行解释成通用百分比，也没有用“在普通知识表中找到了键”替代所有氏族的 `hasTech` 结果。泉水、猫头鹰、窃取/复制知识、征服、战役和其他特殊提供者可能改变有效知识。当前同时保存可读取的特殊提供者存在标记，完整适用关系仍须逐分支验证。

`happiness_cache` 是玩家原生幸福缓存，`consumption_coefficient` 是原生消费系数。兼容字段`population_cache`实际保留资源组件的stored population；普通熊／乌鸦住房人口getter另走`getResource(Population)→computePop`，不能把该存储字段叫作已核的通用人口缓存。Rat有独立使用分支。普通氏族中它为0不表示零人口，也不覆盖已有的人口权重模型。

本次额外核对了 `hasTech #13059`、`setTech #13060` 与 `upgradeUnit #13203`：普通知识由 `MapData → StringMap` 保存，设定知识会写入布尔值；工具/单位升级同样保存于 `StringMap`，升级时写入或递增整数。因而这里导出的条目是原生状态，不是知识描述换算出来的百分比。`hasTech` 在查询普通表之前还检查特殊提供者，工具判定也有单位替代和模式分支，条目本身不能宣称覆盖这些分支。

### 自己区块与建筑

`zones` 只包含自己区块的效果条目和原生 flags。`buildings` 只包含这些区块内、再次验证了身份与归属的建筑，增加：升级级别、扩建标记、伤损/维修读数、效果条目，以及可读取时的港口 `produceChoice`、停止标记和建筑 `state.progress/state.contains`。

这让后续分析可以区分：

- 工人换岗后真正到了哪座建筑、是否已经进入目标区块。
- 同样是水手，港口当时选择的是知识还是声望等副产出。
- 产量变化附近是否发生工具、建筑升级或地方效果变化。
- 矿藏共享进度是否跨过一次提取阈值，建筑是否还保存剩余数量。

`state_progress` 是保留的原生状态输入。只有确认它属于相应矿藏、字段语义与当前建筑种类匹配后，才能解读为开采进度；不能把任何建筑的 progress 都叫挖矿或生产。矿石本来就是共享进度跨阈值后离散入账，不能把静态矿工 q × 时长当作逐人已收到矿物。

本版本这些建筑状态的 `progress/contains` 是 `null<f64>` 装箱字段。采集器显式解包后才导出数值，空值保持 `null`；不会把内存指针误当进度。

## 组件状态怎样验收

`status=ok` 仅表示本组件承诺读取的输入完成了校验；它不代表完整生产模型已经完成。两个 availability 标记依然为 `false`，逐人最终率依然为 `null`。

`status=partial` 表示某些可选字段、本地规则、效果或科技工具表读取失败，或者某个单位/建筑在读取期间发生了变化而被省略。保留的字段仍有局内身份和时间依据；应展示具体缺失项，不能把整行补零。`unknown/rejected` 则不能用于该组件的跨快照推导。

暂停期间 `time_before == time_after` 合法，表示没有经过游戏时间；不能按墙钟时长累计劳动产出。各类模式可以记录自己已知的这些原生输入，但特殊模式与其他氏族没有因此获得完整加成公式。后续分析必须保留父快照 `game_context`，把不同模式和氏族分开验证。

## 3. 本地基础配置的用途和界限

安装时只从参与者自己的已核验游戏安装中生成 `research/static/labor_rules.json`。该文件不提交到公共仓库，采集器也不会上传整个游戏资料库。

本组件实际只使用 `tables.unit` 中的 `id/produce` 和 `tables.resource` 中的 `id/props.converts`。输出只保留候选资源、候选基础 q、所需建筑种类，以及“是否还有其他要求”；不复制文本、美术、全氏族技能描述或任意静态子表。

例如 Farmer 的 Wheat 配置基础量、Wheat→Food 的库存转换，能够说明该岗位的基础生产路径。但冬季农民存在基础值替换，受伤、幸福、工具、建筑、地方效果、知识、氏族能力和事件还会改变结果。不能直接把配置 q 当作该工人此刻产出，也不能把一个职业的所有候选 produce 行相加。

因此即使一个配置候选写着 `q=0.5`，报告也只能说“本机配置候选基础参数为 0.5”，并附 `requirement_status=not_evaluated`。它不能说“这个农民实测每秒 0.5”，更不能忽略生产门控后算整月收入。

## 4. 如何把这部分最终补成可用的劳动收益模型

### 先做受控边际校准

用玩家自己的人类单人局，选择同人口、同季节、同知识/工具/地方效果、没有盛宴/临时事件、没有一次性支出与奖励、库存未到上限的短窗口。

1. 保留该名工人的指派前、职业改变、抵达同地块、生产标签改变等时间区间。
2. 按资源各自的原生缓存时间识别新结算周期；重复读到同一周期不能重复累计产量。
3. 用玩家总毛产出在前后的差、其他工人和各项输入是否稳定，估计这名工人造成的边际率变化。
4. 同时检查总消费、库存差额与积分残差。残差不闭合时保留未知，不自动归因给该工人。
5. 多次重复、分夏冬与相关氏族知识组合记录，不把一个短窗估计推广为永久职业系数。

这得到的是“控制条件下的边际估计”，仍不是直接读取逐人已到账流水。调岗耗时也须拆成不同里程碑的观测区间；指派至总率更新包含走路、职业转换、任务和缓存延迟，不能统称纯走路时间。

### 再逐分支重建可解释公式

建议优先熊族/乌鸦普通单人经济，按“基础值选择 → 生效资格 → 加成分项 → 减益分项 → 最终率”建立版本绑定的纯函数。每一项必须带输入证据、字节码函数/指令证据和覆盖状态。

至少应补齐：

- 有效生产要求、当前单位动态 `inf` 与静态职业配置是否一致。
- 工具、建筑升级、当前地方建筑与地块效果。
- 当前氏族技能、声望阶段、知识与其他有效提供者。
- 临时效果、盛宴、事件、季节、人口相关冬罚、伤病和不幸福。
- 特殊模式、盟友供给和非劳力收入；未知分支必须明确阻止输出完整预测。

最终模型应输出 `modeled_rate` 和解释项，并与原生玩家汇总率做差分验收；不能把模型重建值重命名成 `native_actual_rate`。当前 `model_effective_rate=null` 正是为了给未完成的覆盖留出明确位置。

辅助建议最后才比较：从原岗位抽走该人会少多少、到新岗位何时开始生效、扣除直接转职成本后多久回本、能否更快达到下一项住房/殖民/招兵/知识目标，以及当前食品安全和资源上限约束。不同资源不设一个永久的兑换比价。
