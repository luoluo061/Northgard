# 3v3 本人视角采集与协作说明

**0.5.2-alpha 准备版：可以准备安装和实验采集流程，尚未完成真实 3v3 短测或完整局验收。**采集器读取本地玩家本人，不操作单位、不修改游戏、不执行游戏内 getter，也没有后台上传。

## 一台电脑能看到哪一份数据

一人安装，得到一份本人视角：自己的资源和原生产消缓存、本人单位的 UID／职业／兵种／指派／状态、自有建筑和允许的已知地图。不会自动获得六人的全部经济、命令和地图。

想比较同队三人的人口投入，需要三人各自安装并录下自己的操作。敌队不需要安装；想研究六个视角，也只接收愿意参与者各自提供的本人数据。缺少哪个视角就记录缺失，不从别人的本机内存代采其他玩家。

多人模式的已知地图可能包含队友带来的共享视野。当前尚未可靠区分“本人侦察发现”“共享视野获得”“之前就知道”。因此新加入已知集合的地块不能直接计为本人侦察员的产出。已知地块也不等于当前可见，不会因此导出敌方动态实体。

新增[已知地块资源与野兽组件](KNOWN_ZONE_DETAILS.zh-CN.md)先限定普通单人FreeForAll，**在3v3中返回`unsupported_context`**。这不是没有资源或野兽，而是多人可见性、共享发现和特殊分支尚未验收；本人库存、职业、劳动、增长输入及既有已知几何地图继续独立采集。不能为了补齐这个组件而直接读取队友或敌方经济。

## 原生上下文与玩家标签是两层信息

| 层 | 内容 | 怎样使用 |
|---|---|---|
| 原生模式 | `PlayMode.Multiplayer` 及 `MultiMode.Team3V3` 等变体，`Standard`／`Private`／`Ranked` 等游戏类型 | 表示采集器从本机已验证结构观察到的模式；缺失仍为未知 |
| 原生匿名队伍结构 | 按开局槽位数组 `startPlayers` 与当前存储的 `teamLeader` 关系汇总人数；另存原生模式期望布局、本人队伍序号与一致性 | 不是冻结的开局队伍历史，不含名单、姓名或其他玩家经济；槽数可能包括 AI |
| 贡献者标签 | 共享 UUID、`declared_format`、`team_label`、`player_slot` | 供参与者把独立视角归到同局；不能覆盖原生证据或认证赛制 |

A／B 是参与者约定的队伍标签，1–3 是各队内约定席位，和游戏原生玩家 ID／队伍序号不是同一口径。原生两个队伍各三槽，也不能单独证明有六个人类或六份可贡献数据。当前不导出逐席位真人／AI 区分；读取中数组、关系或时钟变化会拒绝该组件，模式期望与槽位布局不符时布局保持 unavailable。

`Team3V3` 识别成功是模式检查；真实 3v3 的连续读取和完整字段覆盖仍需短测与整局验证。

## 1. 每人安装一次

在自己的电脑读取 [安装流程](INSTALL_WITH_CODEX.md)，运行：

```powershell
git clone https://github.com/luoluo061/Northgard.git
cd Northgard
python scripts/setup_local.py
python scripts/doctor.py
```

需要 Windows x64、64 位 Python 3.11+、支持的游戏双指纹。setup 自动定位 Steam 安装；必要时使用自己的 `--game-dir`。无需 pip、管理员权限或修改游戏文件。`ready_for_local_test` 不意味着已读到对局。

把本地游戏路径、生成规则、原始捕获留在本机，不能把维护者或队友的游戏定义直接复制进公开仓库。

## 2. 组织者为每一局生成协作包

```powershell
python scripts/create_match_kit.py --output ..\northgard-3v3-kit
```

输出目录必须是新目录。该目录包含：

```text
northgard-3v3-kit/
  README.txt
  commands.txt
  A1.metadata.json
  A2.metadata.json
  A3.metadata.json
  B1.metadata.json
  B2.metadata.json
  B3.metadata.json
```

终端和 README 中列出这一局共用的小写 UUIDv4。六份模板使用相同 UUID 和不同席位；模板默认 `mode: "multiplayer"`、`consent_to_share: false`。

组织者只把对应模板和命令分给实际愿意参与的人。生成协作包不发送消息、不打开游戏、不开始录制、不联网提交，也不代替任何人的分享同意。只收 A1／A2／A3 完全可行，未参加的席位保留空缺。

重开另一局要生成新 UUID；同一局的短测和正式捕获可共用该局 UUID，但它们是不同采集覆盖，不能把短测文件伪装成完整局。不要重用输出目录覆盖已有捕获。

建议在另一测试局完成短测，正式局从开局持续记录。当前每局每个已知席位只接收一份贡献；若同一局分开做了短测和正式捕获，选择一份贡献并注明实际覆盖，短测留本地，不把两份同席位数据同时入库。当前没有自动跨采集拼接或补齐缺口的功能。

## 3. 本人进入对局后短测

以下为 A1 示例，先替换 UUID；其他参与者使用自己的席位：

```powershell
python collector/collect.py --seconds 120 --interval 0.5 --out-dir captures/3v3-short-A1 --shared-match-id "<这局的共享UUID>" --declared-format 3v3 --team-label A --player-slot 1
```

`commands.txt` 的命令默认持续记录，首次短测须加 `--seconds 120` 并换一个短测目录。只想先验证自己能否采集，不必等待队友全部装完。

标签参数的规则：

- `--shared-match-id` 必须是规范小写 UUIDv4。
- 填队伍、席位或声明赛制时必须同时给共享 UUID。
- `--team-label` 为 A、B 或 unknown；指定席位时必须是 A 或 B。
- `--player-slot` 为 1、2、3；无把握时省略，元数据保留 null。
- `--declared-format` 为 3v3 或 unknown，只表达参与者声明。

使用相同 UUID 只表示“我们认为这些视角属于同一局”，不授予队友数据访问，也不自动同步电脑时钟或验证座位唯一性。

## 4. 短测应该核对什么

短测由玩家正常操作，Codex 只查看采集结果。在这版尚未实局验收的前提下，应如实记录以下成功、partial、rejected、缺失或冲突情况：

1. **本人身份**：采集的是正在玩的本地人类玩家，资源变化与自己的画面一致，不是旁观者或 AI。
2. **原生模式**：是否出现 Multiplayer／Team3V3，匿名槽位按当前关系汇总的布局与原生模式期望是否可读、一致；不要用玩家手填标签补充原生未知。
3. **游戏时间**：覆盖哪年哪月；若发生暂停，记录仍可写出，但模拟秒不增加，不累计暂停劳动时长。
4. **基础经济**：本人粮木金库存和产消缓存是否可读；更新时钟、竞态和错误是否保存。
5. **职业与兵种**：本人 UID／kind、指派、任务和位置是否连续。其他氏族住房人口未知时不以单位数量代替。
6. **新组件**：劳动／加成输入、市政厅进度、支付与地图分别检查状态。生产候选不等于逐人实产，未知不能填 0。
7. **范围**：共享视野来源未确定的地块标为本人已知，不能声称是本人亲自发现；没有名单、队友／敌方经济或隐藏动态实体。
8. **断线与停止**：重连和读取失败保留分段；短测停止不代表游戏终局。

记录短测的实际覆盖和缺失即可，不要求为了通过验收改变玩家正常战术。需要安排专门的控制变量实验时，另行说明实验操作与目标。

## 5. 正式记录与停止

短测结果符合参与者这次实验目标后，依玩家安排使用新目录、省略 `--seconds` 持续录制：

```powershell
python collector/collect.py --interval 0.5 --out-dir captures/3v3-full-A1 --shared-match-id "<这局的共享UUID>" --declared-format 3v3 --team-label A --player-slot 1
```

`--seconds` 是墙钟录制上限，不是游戏月份。游戏加速、暂停、网络等待都不能直接换算为相同的生产时间。所有分析以 `game_time_seconds` 为准。

停止可按 Ctrl+C，或在这次输出目录建立 `STOP` 空文件；支持的游戏结束标志也会触发结束。等待最终 `manifest.json` 的 `recording_state: "stopped"`。采集开始较晚、断线、提前退出、短测停止都要如实标明，不等于完整局。资源或职业读到一帧，也不等于劳动／增长整条链都可用。

## 6. 完善标签与经验

在自己的模板里填写氏族、地图／难度已知项、经验水平、目标、结果和反馈。共享连接对象只有这四个字段：

```json
{
  "shared_match_id": "00000000-0000-4000-8000-000000000001",
  "declared_format": "3v3",
  "team_label": "A",
  "player_slot": 1
}
```

上面的 UUID 只用于展示格式，真实记录必须使用本局协作包的随机值。它放在元数据 `match_link` 中；完整模板由协作包或 `schemas/metadata.multiplayer.example.json` 提供。记录 CLI 已填写的标签保存在本机 manifest，导出时与元数据核对；双方非空值冲突会拒绝，不能靠随机覆盖解决。

`consent_to_share: false` 表示尚未允许公开贡献。审阅后由贡献者决定是否同意分享；代码、模板、队友或组织者不能替他同意。公开 fork 和 PR 已经是公开发布，不是“合并之后才公开”。

经验应连接 A 年月／月段与游戏秒，例如：“A802 年 7 月中，我把农民转水手是为了一起出兵，想比较少掉的粮食与更早凑齐克朗的价值。”战术目的写本人理解即可，不粘贴语音、聊天、姓名、Steam ID 或账号。详细格式见 [PLAYER_FEEDBACK.md](PLAYER_FEEDBACK.md)。

## 7. 本地导出、验证和公开回传

采集停止后，参考 [贡献协议](DATA_CONTRIBUTION.md)：

```powershell
python scripts/prepare_submission.py --capture captures/3v3-full-A1 --metadata ..\northgard-3v3-kit\A1.metadata.json --output submissions-review
```

导出器生成脱敏压缩流、摘要、标签和校验文件，不执行上传。先阅读 `SUMMARY.md` 和 `submission.json`，运行验证器并抽查数据。输出 UUID 是这份提交的身份；共享 UUID 是整局的协作标记，两者不可互换。

所有多人贡献都标记 **`experimental_multiplayer_unverified`**，包括原生成功识别为 3v3 的贡献。单人增长门槛和盛宴报价模型不在多人上输出；原生储存进度、缓存和实际保存的支付输入仍可独立保留。未知来源／特殊模式／字段缺失继续保留其质量信息。

有本人向此公开仓库贡献这一局的授权时，按文档使用 fork、数据分支和 PR；缺少授权则先完成审阅，再说明范围并询问。上传失败不改用其他目标偷偷回传。每份数据只进入 `data/submissions/` 的已审阅目录，不能递归打包整个 captures。

## 之后怎样把几个视角连起来

共享 UUID 用于分组，各份贡献仍按自己的 session／run／segment 保存原始游戏时钟、错误、缺口、单位和地图。未来统一分析应先检查：

- 是否同一真实对局，原生赛制与自报标签是否冲突。
- A／B 席位是否重复，是否有短测与正式记录的覆盖重叠，是否缺少部分队友。
- 各视角的模拟时间覆盖能否对齐；共享 UUID 不证明时钟已同步。
- 单位 UID、玩家实体 UID、地块 ID 仅在各自上下文使用，跨机实体映射必须另有证据。
- 每人是否独立授权贡献，输入范围是否仍为本人；不能从一份贡献替另一人推断资源或操作。

可以比较同一月份各人的劳力用途、资源预算和目标期限，再关联各自提供的解释。不能从一人“此时缺粮”推出队友的实际库存，也不能把一个局部短窗系数当成六人和所有氏族通用的效率。
