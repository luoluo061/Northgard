# 从理解经济到形成战略：具体怎样研究

本计划回答“尚不知道该追求什么，研究从哪里开始”。研究入口是可检验的机制问题：人口带来哪些生产能力和负担，各项投资会解锁什么，不同氏族有哪些可行发展路径。战略目标在这些关系清楚后，再由地图、威胁、玩家偏好和对局信息逐步形成。

先补足游戏语境：[氏族分工、攻略与解说资料](STRATEGY_ROLES_AND_GUIDES.zh-CN.md)整理清野、视野、发育转军和支援的实战用途。攻略中的具体决策产生研究问题，再由下列方法验证；不能只从普通采食者模型推导一套打法。单挑需要自理的任务与3v3约定分工分别分析，社区经验与代码规则分别保留证据。

已完成的具体离线研究见[熊、乌鸦与猞猁的战略因果案例](CLAN_STRATEGY_CASES.zh-CN.md)。它将路线拆成前置、门控、状态反馈、投入与失败条件；局部分支核验和条件演算没有升级成控制实测或最优策略。

研究日期：2026-10-27。条件模型绑定`v4.3.29.43337 / Steam Build 25096976`，双指纹和六条基础规则见[rules.v1.json](../mechanics/rules.v1.json)。本页数表由现有离线模型重算；不包含个人对局数据，也没有启动新局或控制实验。

## 1. 先完成哪些东西

| 顺序 | 要回答的问题 | 交付物 | 进入下一层需要什么 |
|---|---|---|---|
| 实战理解 | 这一赛制中，谁清关键地、谁开图、谁支援、何时交战 | 有来源和版本的氏族职责／实战案例 | 确认作者实际主张与适用赛制；视频仅简介可读时不声称观看，未知安排不补造 |
| 口径 | 什么叫一个人口、一个粮工、一秒劳动、一笔到账 | 字段与时钟来源表 | 住房人口、实体数、消费权重、指派与有效工作分开；缓存有自己的时点 |
| 人口经济 | 维持当前人口需要多少劳动，新增一人改变什么 | 有条件的粮耗、粮产、取暖、出生账本 | 指定条件下先解释原生毛产和消费，再核库存；反例保留 |
| 能力转换 | 地块、建筑、知识、工具和军队的投入形成什么 | 转换卡与前置关系图 | 费用、占人、等待、投产、持续负担与失效条件有证据 |
| 氏族路线 | 熊、乌鸦怎样改变上述关系和合法行动 | 各自的规则差异与可行路线 | 逐个效果核条件；配置存在、已经获得、当前生效分别记录 |
| 局面判断 | 当前有哪些路可走、缺什么、付出什么 | 可行方案及其资源／能力变化 | 输入足够，未知有边界；此时结合偏好和威胁形成目标 |
| 操作建议 | 为选定目标，怎样安排更合适 | 条件建议、替代方案及解释 | 同起点完整比较，预测经过未用于拟合的窗口复核 |

各层交叉迭代。先跑通一个小机制的证据链，再把它接到复杂转换里；不需要等所有氏族完整解码才开始验证普通人口。

## 2. 第一批只研究人口经济

| 问题ID | 具体问题 | 当前依据与状态 | 下一步验收 |
|---|---|---|---|
| P01 | 什么状态下，一个村民真正开始／停止采食 | 基础q与部分资格分支已核；职业／produce标签不能独立证明实际工作 | 用已有任务、位置、指派和缓存时钟描述过渡；无法确定的边界保留区间；E1/E3验证 |
| P02 | 当前这批单位一共吃多少粮 | 人口规模项和逐单位倍数分开；同质条件公式可运行 | 固定身份、模式、P和效果，独立比较消费；再做不同P档的E2 |
| P03 | 固定人口下，多少劳力能满足食物稳态约束 | 可由已核条件模型计算 | 输入必须满足条件；不能直接当实际分工建议或过冬预算 |
| P04 | 增加一人，全体食耗增加多少 | 可计算`C(P+1)-C(P)` | E2检验多个P档；同时确认新增成员消费资格，不能只计算新人自身食耗 |
| P05 | 幸福与住房怎样产生下一名劳力 | 熊／乌鸦普通单人FreeForAll路径已核部分增长／门槛，完整动态bonus和出生门控未闭合 | E4分离进度、增长率、住房、实际出生；先报告条件结果 |
| P06 | 转岗期间损失多少有效劳动 | 已有UID、任务、指派、位置及标签链；没有完整个人到账表 | E3分开接单、移动、职业变化、有效工作与缓存更新；不把整段都称为走路 |
| P07 | 维持人口还占用多少木材与其他资源 | 普通取暖和维护分支部分已核 | 明确取暖人数、羊和地块作用顺序，分季节核木耗，不能用P直接替代全部人数口径 |

优先顺序为P01/P02/P03/P04，再接P06、P07和P05。先利用已保存的数据检查时钟和稳定窗口；只有已有样本不能识别的问题，才进入[小实验计划](MECHANICS_VALIDATION_PLAN.md)。完整对局适合观察路线，小实验适合分离机制，两者承担不同证据。

## 3. 第一份人口表：已经能算到哪里

以下**全部是条件演算**：固定普通人类单人经济、熊／乌鸦、健康、非冬季、有效连续采食；每人食耗倍数1，难度／特殊消费系数均为1；无其他加减成、贸易、支付、封顶、饥饿或人口变化。CLI不会验证真实局面是否满足这些条件。

```text
单名有效采食者毛产 g = 0.4粮/游戏秒 = 24粮/游戏月
人均基础食耗 b(P) = 0.1 × (1 + sqrt(P/46))
同质全体食耗 C(P) = P × b(P)
食物稳态净流非负所需采食人数 = ceil(C(P)/g)
增加一人的全体食耗增量 = C(P+1) - C(P)
```

| 固定人口P | 全体每月食耗 | 食物稳态非负的最少采食人数 | 仅在此食物约束下剩余的人数 | 从P增至P+1，全体每月新增食耗 |
|---:|---:|---:|---:|---:|
| 5 | 39.891 | 2 | 3 | 9.111 |
| 10 | 87.975 | 4 | 6 | 10.299 |
| 15 | 141.394 | 6 | 9 | 11.224 |
| 20 | 199.126 | 9 | 11 | 12.008 |

最后一列是新增一名普通成员之后的**全体**月食耗差，不是这名新人的个人账单。实际人口在月中变化时，要按各段人口积分；这张表没有预测出生时间。

“剩余人数”也不等于可随意使用的实际劳力：其他岗位、住房、取暖、维护、殖民、备粮、侦察和军事负担还没纳入。库存能够支持短期负收支，故该列不是每时每刻必须维持的采食比例。

同样固定P=10，只改变已核冬季分支时：

| 条件 | 每名采食者月毛产 | 全体月食耗 | 食物稳态非负最少采食人数 |
|---|---:|---:|---:|
| 非冬季基线 | 24.000 | 87.975 | 4 |
| 乌鸦普通冬季基线 | 16.000 | 87.975 | 6 |
| 熊冬季，无冬节 | 18.400 | 87.975 | 5 |
| 熊冬季，冬节生效 | 18.400 | 61.583 | 4 |

这说明“一个人养几个人”必须带人口规模、岗位、季节、氏族和效果条件。数表描述规则关系，不给任一实际开局下结论。当前证据是`code_derived_not_controlled_live_validated`；控制实验仍为`not_run`。

复算工具见[基线模型](../mechanics/README.md)。例如在仓库根目录运行：

```powershell
python mechanics/baseline.py --population 5 --gatherers 2 --clan Bear --season non_winter
python mechanics/baseline.py --population 10 --gatherers 4 --clan Raven --season winter
python mechanics/baseline.py --population 10 --gatherers 4 --clan Bear --season winter --winter-festival
```

将人口分别设为5／10／15／20，读取`model_estimate`中的食耗、最少粮工、剩余人数和新增成员食耗增量，均可重算第一张表。每月统一60游戏秒；[官方时间接口](https://northgard.net/doc/api/current/GameState.html)提供日历口径，本机编译分支另已核。数表是固定状态的60秒等价量，不是未来库存预测。

## 4. 每条规则都要有一张机制卡

机制卡的核心问题是“在什么条件下，输入会怎样改变输出”。分别登记三种状态：**代码是否核过、实际输入是否可取得、控制实验是否通过**。它们不能合成一个笼统的“已验证”。

| 字段 | 内容 |
|---|---|
| 标识与版本 | 规则ID、修订、本机双指纹；函数编号只对该编译版本有效 |
| 问题和范围 | 解释什么，适用氏族／模式／状态，明确排除什么 |
| 输入 | 名称、单位、来源、读取时点、可观测程度、缺失时的处理 |
| 规则与输出 | 数学表达／状态变化；输出单位和含义 |
| 证据 | 配置字段／函数位置／观察窗口／实验ID分别支持哪项结论 |
| 验证 | 预测、观察、误差、排除原因、反例、留出复核窗口 |
| 未知与下一步 | 尚不能确定的分支，以及能区分候选解释的最小检查 |

例如P02的住房人口输入使用已核父级人口口径，单位食耗倍数需要逐单位资格；生产人数不能仅由职业标签计数；消费与生产缓存必须保留自己的更新时间。储存字段`population_cache`不能替代普通住房P，资源组件同名增长槽不能替代市政厅进度。

## 5. 人口闭合后，怎样接能力转换和氏族

转换卡在机制卡上再记录：**一次性费用、劳动占用、移动／施工／转岗等待、持续负担、解锁能力、前置与失效条件**。

首批转换链选用同一组基础规则逐步组合：

1. 取得地块 → 建造生产建筑 → 到岗 → 有效产能；土地资源存在、建筑完成、实际生产分别核验。
2. 建房／升级 → 容量或增长条件变化 → 实际出生 → 有效劳动，同时加入新增全体消费。
3. 挖矿 → 达提取阈值 → 取得矿物 → 锻造或升级 → 指定岗位／单位获得效果。
4. 产知识 → 达具体门槛 → 合法获得知识 → 效果在指定人、地块和状态生效。

共同机制跑通后，先给熊和乌鸦增加规则差异：开局条件、合法支付、消费／冬罚、独有岗位、知识前置、声望触发与技能。不能只给全体产量套一个氏族系数，也不能把两族局部核验扩成所有氏族已完成。

此时才整理发展路线：每条路线列明能形成的状态、缺失前置、资源向量、维持负担、所需时间及未知条件。60／120／240游戏秒可以作为统一观察尺度；它们用于展示发展可能，不要求玩家把某个状态当作战略目标。

## 6. 采集器接下来怎样服务研究

先为每个问题建立“需要哪些输入、现有字段能给哪些、还缺什么”的来源矩阵。缺字段必须对应某条具体规则或候选解释，再决定是否扩展读取；新增JSON字段数量不作为研究完成指标。

对账严格按顺序进行：

1. 核身份、模式、条件和数据质量，保留原始缺口和失败记录。
2. 把任务／指派／位置与原生缓存按各自时点对齐；不同更新周期不能硬作同一瞬间。
3. 独立比较模型毛产、模型消费和原生汇总；未知资格给区间或条件结果。
4. 按原生更新时钟核库存，单列费用、奖励、上限／下限和离散提取。
5. 反例推动规则或读取解释的修订；局部吻合只支持已检查的条件。

下一份有意义的结果应能回答：“这段时间里，这些人实际处于哪些阶段，为什么产生了这些粮食和消费，哪些差额仍解释不了。”随后再加入木材、出生和投资。当前没有启动新采集、执行游戏getter、自动操作游戏或公开上传个人对局；实验运行仍按玩家的具体安排进行。
